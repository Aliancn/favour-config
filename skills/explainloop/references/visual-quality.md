# Visual quality direction

Use this when designing or reviewing a GIF. The values below are starting points for a 960 × 540 **logical canvas**, not rigid limits; inspect the high-resolution output at its intended display width. For square and portrait variants, establish a new reading path and type hierarchy instead of scaling the landscape arrangement into the new frame.

## Diagnose before decorating

The first generation of demos looked generic because every subject used the same title rule, footer line, small cards, and fade-in sequence. A palette cannot create a distinct art direction by itself. For each scene, choose **one visual thesis**: the object the viewer should notice first, the action that changes it, and the conclusion visible in the final state. If the key object is too small, remove secondary cards before adding decoration.

Choose the background after locating the focal object. Test the first frame at thumbnail size: the focal object and reading path should remain evident without relying on captions. Treat the canvas, content surface, and accent as distinct roles. A texture, grid, corner mark, or gradient should explain structure or evoke a concrete material; remove it if it competes with the claim. See [backgrounds.md](backgrounds.md) for original compositional recipes and public references.

For a more eye-catching canvas, use one background effect with a clear purpose: soft light to orient reading, edge glow to locate a system node, broad matte planes to separate object layers, or a local motif to frame evidence. Keep the effect fixed across GIF frames. Inspect the rasterized GIF for gradient banding or texture shimmer; source SVG smoothness does not guarantee a clean 256-color result.

## Typography and spatial hierarchy

- Use a deliberate type ladder: a large claim/headline, a medium label or value, and a smaller source/context tier. At 960 × 540, try roughly 36–48 px, 20–28 px, and 18–20 px; reserve 14–16 px for truly optional metadata. Judge the rendered GIF at its actual article width: at 720 px landscape or 360 px portrait, aim for at least about 14 px for essential text and 12 px for provenance. Remove copy or reflow before shrinking type. Use no more than two type families in a frame.
- Give visible copy a job: identify the object, explain the changing relation, or establish source status. Remove invented section numbering, English eyebrow labels, fake archive IDs, and repeated metadata when they do not carry evidence. A scene should still be recognizable with its palette temporarily ignored; if every topic becomes the same header plus cards, recompose it.
- Choose type for the passage, not the style label: an editorial quote may benefit from a serif; UI fields need a stable readable face; a large display numeral may use a distinct Latin face. One family can be enough. Compare two installed pairings before settling on one. Check `fc-match` and a rendered Chinese specimen: a missing named font can resolve to a Latin font and silently change metrics or glyphs. Do not bundle system fonts; the optional font choices and their sources are in [font-catalog.md](font-catalog.md).
- For Chinese, make breaks by meaning and avoid a closing punctuation mark at line start or an opening mark at line end. Keep numbers with units and short Latin terms intact. A display font should never carry long text merely because it looks distinctive. Pairing is successful when the article's object and values remain easiest to read.
- Align the left edges and baselines of related text. Use a consistent spacing rhythm (for example 8, 16, 24, 40 px). Keep important content away from the outer edge and reserve enough interior padding for the longest label. Manual line breaks via `kit.textLines` are preferable to a crowded single line; inspect truncation rather than guessing character widths.
- Give the primary object a larger visual footprint than its supporting objects. Use one clear reading path. `kit.page` is a convenient explainer layout, not a mandatory frame: use `kit.svg` for a scene-specific composition when the repeated header/caption frame weakens the explanation.
- Target at least 4.5:1 for ordinary text and 3:1 for meaningful graphics against adjacent colors, following WCAG. Thin 1 px strokes can still disappear after GIF quantization; use stronger strokes or a text label for the crucial relation. Do not encode state in color alone.

## Semantic UI details

- Treat a UI widget as a small information structure, not a themed rectangle. An email can show sender, subject, preview, and time; a calendar event can show date, title, time, and status; a message can show speaker, text, and timestamp. Use `emailCard`, `eventCard`, and `chatMessage` where those details are supported by the source or explicitly identified as illustrative.
- For each field, distinguish quoted source data, a clearly labeled synthetic detail, and an unsupported inference. A state transition needs an evidence-backed trigger and outcome; do not show a success badge merely to complete the animation. On portrait layouts, remove optional chrome and metadata before shrinking primary fields.
- Preserve the source's status. A generic UI mockup may illustrate a workflow, but it must not look like a screenshot of a real product or add unreported success states. Label a synthetic example as such in `meta.sourceRefs` and the on-screen context when relevant.
- Keep icon sizes, border weights, corner radii, and padding coherent within a scene. An icon supports recognition; a label carries the precise meaning. Use state changes such as queued → in progress → done only when the text supports those states.

## Motion choreography

- Design the complete outcome frame before animation. It should read as an intentional still: the focal object, direct labels, and conclusion remain clear when paused. Work backward to the trigger and opening state. If movement only reveals a finished poster, simplify the motion or choose a different relationship.
- Plan an orientation, trigger, transformation, and readable outcome. A 5-second loop might spend roughly 0.4 s orienting, 0.5–1 s on the trigger, 1.5–2.5 s on the causal action, and the remainder on the result; adapt to the idea. The opening frame should already establish a useful object or context, and the final state should be understandable when paused.
- Treat motion as a sentence: the viewer should be able to name what changed, where an object went, or why a result followed. Keep a semantic object visually stable across states. Use entrance fades to support that change, not as the entire explanation. Let only one primary event demand attention at a time.
- Keep an object visually continuous as it moves between states or locations. Animate a meaningful property (route, selection, count, status, chart extent), not a progress bar added solely to make frames differ. Show cause before effect; related objects should move in a coordinated direction.
- When several pieces belong to one moving card or panel, drive them from one master progress and derive their entry phases by importance. Reverse that progress on exit to reverse their order. A soft stop suits a panel reaching a boundary; a small spring-like settle suits a floating element only when it cannot reflow neighboring text. The curves in `kit.motion` are starting points, not mandated durations.
- Use shorter, quieter motion for UI state feedback; reserve larger expressive motion for a rare turning point. Carbon describes productive vs expressive motion and gives fast-to-slow duration examples. For this noninteractive GIF, use those as rhythm cues, not as literal UI response requirements.
- Check loop reset: if the final frame differs sharply from the first, use a natural pause, reverse, or a clear scene restart. Do not make the reader wait through a long motionless ending. GIF's centisecond frame delays mean 30 fps is approximate; judge smoothness by playback, not frame count alone.

## Data and evidence

- Put values and units next to the mark they explain. Direct labels beat a distant legend for a small chart. Choose scales that preserve the claim; a comparison bar chart should normally start at zero. Show uncertainty, qualifiers, and source status where they affect the conclusion.
- Animate data from its actual baseline to its reported value. Do not reveal a final label against an incomplete bar unless clearly presented as a target. Keep a source note close enough to the chart that it survives cropping or reuse.

## Review at delivery size

When the active agent can actually perceive image pixels, inspect the opening, action midpoint, outcome, loop edge, and eight-frame temporal strip using `scripts/preview.mjs --temporal-strip` at the width the GIF will appear in the article. For batches, compare the outcome frames using `scripts/preview-batch.mjs`; the metadata check alone cannot see scene-local colors or fonts. Look for font fallback, tiny labels, clipping, overlapping arrows, faint lines, empty opening frames, unsupported UI states, and an abrupt loop. Fix concrete defects and rerender, with at most two visual revision rounds. Without image perception, skip visual review and report that limit; `inspect.mjs` verifies technical output but cannot judge visual polish.
